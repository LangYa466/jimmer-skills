# Jimmer ORM — Java

Jimmer is a compile-time ORM for the JVM. Entities are **interfaces**; an annotation processor (`jimmer-apt`) generates immutable implementations, drafts, a typed SQL DSL and object fetchers. Its core idea: read and write **object graphs of arbitrary shape** as a whole.

> Baseline: Jimmer **0.12.4** (latest at time of writing). Every API shown in this skill was compiled and executed against 0.12.4 + H2. Several APIs in older blog posts and parts of the official docs no longer exist — see [Critical rules](#critical-rules-read-first).

## Mental model

1. **Entities are immutable, dynamic interfaces.** A property can be *unloaded* (absent) — that is different from `null`. Reading an unloaded property throws `UnloadedException`; Jackson simply omits it.
2. **Create/"modify" objects with drafts** (`Immutables.createBook(draft -> ...)`, `BookDraft.$.produce(base, draft -> ...)`). The original object never changes.
3. **Read graphs with object fetchers** (`BookFetcher.$.allScalarFields().store(...)`) or DTO classes generated from `.dto` files. No N+1: associations are batch-loaded.
4. **Write graphs with save commands** (`sqlClient.save(entity)`): unloaded props are not touched, loaded props are written, associations are diffed and synchronized according to `SaveMode` / `AssociatedSaveMode`.
5. **Everything goes through `JSqlClient`** — a stateless, thread-safe entry point (no session, no dirty checking, no lazy proxies).

## Generated types (per entity `Book`)

| Generated | Use it for |
|---|---|
| `BookDraft` (+ `BookDraft.$.produce(...)`) | create / copy-modify immutable objects |
| `BookProps` (`BookProps.NAME`, ...) | typed property references (save options, `ImmutableObjects.isLoaded`, sorting) |
| `BookTable` / `BookTableEx` (`BookTable.$`) | SQL DSL. `TableEx` additionally allows joining collection associations |
| `BookFetcher` (`BookFetcher.$`) | object fetcher DSL |
| `Immutables`, `Tables`, `TableExes`, `Fetchers` (generated in the **common parent package of all entities of the module** — adding an entity in another package moves them) | `$`-free style: `Immutables.createBook`, `Tables.BOOK_TABLE`, `Fetchers.BOOK_FETCHER` (interfaces can be `implements`-ed to use constants unqualified) |
| From `src/main/dto/*.dto` | `View<Book>` / `Input<Book>` / `JSpecification<Book, BookTable>` classes |

Generated code lives in `build/generated/sources/annotationProcessor/java/main` (Gradle) or `target/generated-sources/annotations` (Maven). It appears after compiling.

## Quick start

```groovy
// build.gradle — Spring Boot users: use jimmer-spring-boot-starter instead of jimmer-sql
dependencies {
    implementation "org.babyfish.jimmer:jimmer-sql:${jimmerVersion}"
    annotationProcessor "org.babyfish.jimmer:jimmer-apt:${jimmerVersion}"
}
```

```java
@Entity
public interface Book {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    long id();                         // id must be non-null (long, not Long)
    @Key String name();                // business key used by save commands
    @Key int edition();
    BigDecimal price();
    @Nullable @ManyToOne BookStore store();   // Java: non-primitive types are NON-NULL unless @Nullable
    @ManyToMany List<Author> authors();       // collections are never null
}
```

```java
JSqlClient sqlClient = JSqlClient.newBuilder()
        .setConnectionManager(ConnectionManager.simpleConnectionManager(dataSource))
        .setDialect(new PostgresDialect())
        .build();                       // Spring Boot starter creates and injects it for you

BookTable t = BookTable.$;
List<Book> books = sqlClient
        .createQuery(t)
        .where(t.name().ilikeIf(name))                  // *If: skipped when arg is null/""
        .where(t.store().name().eqIf(storeName))        // implicit join
        .orderBy(t.name().asc(), t.edition().desc())
        .select(t.fetch(BookFetcher.$.allScalarFields().store(BookStoreFetcher.$.name())))
        .execute();

long id = sqlClient.save(Immutables.createBook(d -> {
            d.setName("SQL in Action").setEdition(1).setPrice(new BigDecimal("49.9"));
            d.setStoreId(2L);           // available when an @IdView exists; else d.applyStore(s -> s.setId(2L))
        }))
        .getModifiedEntity()
        .id();
```

## Critical rules (read first)

1. **No `insert()/update()/merge()` on `JSqlClient` in 0.12.** Use `save(entity)` (UPSERT + REPLACE), `save(entity, SaveMode, AssociatedSaveMode)` or `saveCommand(entity).setMode(SaveMode.UPDATE_ONLY).execute()`. (`insert/update/merge/insertIfAbsent` exist only on repository abstractions: `JavaRepository`/`AbstractJavaRepository`, `JRepository`.)
2. **Java nullity:** primitives are non-null, boxed types are nullable, every other type is **non-null unless annotated with an annotation named `@Nullable`/`@Null`** (prefer `org.jetbrains.annotations.Nullable`). `@Id` must be non-null; `@OneToMany`/`@ManyToMany` lists are non-null. A `@ManyToOne` via join table, fake FK, filtered target or remote association must be `@Nullable`.
3. **Unloaded ≠ null.** For saves: unloaded props are left unchanged; `null` writes NULL. For queries: only fetched props are loaded. Check with `ImmutableObjects.isLoaded(obj, BookProps.STORE)`.
4. **`save()` defaults to `SaveMode.UPSERT` + `AssociatedSaveMode.REPLACE`.** REPLACE dissociates associated rows missing from the collection you pass. Use `AssociatedSaveMode.MERGE`/`APPEND` when you only add.
5. **Objects without id need complete `@Key` values** (or `setKeyProps(...)`, or `INSERT_ONLY`/`NON_IDEMPOTENT_UPSERT`), otherwise `SaveException.NeitherIdNorKey`. With a key containing a `@ManyToOne` (e.g. `TreeNode(name, parent)`), the root object must set `parent` explicitly (even to `null`); children get it implicitly.
6. **`@Formula` lives in `org.babyfish.jimmer.Formula`** (not `...sql`). Java formulas are `default` methods with `dependencies`; only SQL formulas (`@Formula(sql = "...%alias...")`) are usable in the DSL.
7. **Top-level queries cannot join collection associations** — use implicit subqueries `table.authors(a -> ...)`, real subqueries, or `table.asTableEx().authors()` (+ `distinct()`).
8. **Static predicates treat `null` specially:** `eq(null)` → `is null`; other operators reject `null`. Use dynamic predicates (`eqIf`, `ilikeIf`, `betweenIf`, …) for optional filters.
9. **`findById` returns `null` if absent; `findOneById` throws.** Without an object cache they run a normal query, so global filters and logical deletion apply. With an object cache, a cache *hit* is returned without re-checking filters (a miss is loaded with filters) — use an explicit query when filter semantics matter.
10. **Jackson:** in 0.12 the module is `org.babyfish.jimmer.jackson.v2.ImmutableModuleV2` (Jackson 2) or `...v3.ImmutableModuleV3` (Jackson 3). The old `ImmutableModule` class no longer exists. The starter registers them automatically.
11. **Projects without entities but with `.dto` files** (or Web controllers for client generation) still need `jimmer-apt`, and Java needs `@EnableDtoGeneration` on any class in that module.
12. **`@TypedTuple` must be a class** with an explicit all-args constructor (or no-arg constructor) — Java `record`s are rejected by jimmer-apt 0.12.4.
13. **REST client exceptions are declared with Java `throws XxxException`** (exception classes generated from `@ErrorFamily` enums). There is no `@ThrowsAll` in 0.12.
14. **Keep the column on the left of comparisons** (`t.price().lt(x)`, `table.price().lt(values.newNumber(P))`). 0.12.4 renders a constant-on-the-left comparison such as `Expression.numeric().value(x).gt(col)` with the *negated* operator (`col <= x`) — silently wrong results.
15. **Spring Data `JRepository` derived-query parameters are dynamic only with `@DynamicParam`**; a null argument otherwise throws `NullPointerException`.

## Everyday templates

**Typed fetcher constants** (implement `Fetchers` to drop the prefix):
```java
public class BookService implements Fetchers {
    static final Fetcher<Book> DETAIL = BOOK_FETCHER
            .allScalarFields()
            .store(BOOK_STORE_FETCHER.name())
            .authors(AUTHOR_FETCHER.firstName().lastName(), cfg -> cfg.batch(32));
}
```

**Paging with dynamic filters and client-provided sort:**
```java
Page<Book> page = sqlClient.createQuery(t)
        .where(t.price().betweenIf(minPrice, maxPrice))
        .where(t.authors(a -> Predicate.or(a.firstName().ilikeIf(author), a.lastName().ilikeIf(author))))
        .orderBy(Order.makeOrders(t, sortCode))          // e.g. "store.name asc, edition desc"
        .select(t.fetch(fetcher))
        .fetchPage(pageIndex, pageSize);                 // pageIndex starts at 0
```

**DTO in, DTO out** (`src/main/dto/Book.dto`):
```
export com.example.model.Book -> package com.example.dto

BookView { #allScalars  store { id name }  authors { id firstName lastName } }
input BookInput { #allScalars  id(store)  id(authors) as authorIds }
specification BookSpecification { like/i(name)  ge(price)  le(price)  associatedIdIn(store) as storeIds }
```
```java
List<BookView> views = sqlClient.createQuery(t).where(spec).select(t.fetch(BookView.class)).execute();
long id = sqlClient.save(input).getModifiedEntity().id();
```

**Partial update without loading:**
```java
sqlClient.saveCommand(Immutables.createBook(d -> d.setId(id).setPrice(newPrice)))
        .setMode(SaveMode.UPDATE_ONLY)
        .execute();
```

**Delete** (logical if the entity has `@LogicalDeleted`, physical otherwise):
```java
sqlClient.deleteById(Book.class, id);
sqlClient.deleteById(Book.class, id, DeleteMode.PHYSICAL);
```

## Working style for agents

- Before writing DSL code, open the entity and confirm property names, nullity and which props are `@Key`/`@IdView`. Generated method names mirror entity property names (`table.storeId()` exists for any `@ManyToOne store` even without an `@IdView`).
- After changing entities or `.dto` files, **recompile** so `jimmer-apt` regenerates code; stale generated code is the #1 cause of "cannot find symbol" errors.
- Prefer fetchers/DTOs over manual tuple mapping; prefer `save()` with the right mode over hand-written update statements.
- When unsure about a signature, consult the reference file for the topic instead of guessing from JPA/Hibernate habits — Jimmer semantics differ (no cascade config, no owning-side rules for saves, no lazy loading).
